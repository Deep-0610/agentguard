# AgentGuard Control Plane — Production Deployment Runbook

> **Release status:** controlled design-partner / private-preview deployment only. This runbook hardens deployment operations; it does not certify the product for regulated or unrestricted enterprise production. Complete the release gates at the end before offering a general-availability security commitment.

## Deployment topology

- Run the control-plane API on a private application network. Publish it only through a maintained reverse proxy or managed ingress that enforces TLS 1.2+, request-size limits, sane connection limits, and access logging with authorization headers redacted.
- Keep PostgreSQL private. Use a dedicated database and database role with only the privileges required by the service and migrations. Use TLS with certificate and hostname verification (sslmode=verify-full).
- Keep OPA private and reachable only by the control-plane service. Use HTTPS with certificate verification in production.
- Store the API-key pepper, database credentials, and TLS private keys in a managed secret store. Never commit .env, place secrets in image layers, or paste one-time bootstrap keys into tickets or chat.
- Pin container images by digest in the deployment platform. The Compose file is a local evaluation baseline, not a complete production topology.

## Required production configuration

Set:
- AG_ENV=production
- AG_DATABASE_URL=postgres://.../agentguard?sslmode=verify-full
- AG_OPA_URL=https://opa.internal.example
- AG_API_KEY_PEPPER to a cryptographically random value generated by a secret manager (at least 32 bytes of entropy; do not use a human password).
- AG_LISTEN_ADDR to a private interface/port behind the TLS ingress.
- Explicit positive AG_READ_TIMEOUT, AG_WRITE_TIMEOUT, AG_IDLE_TIMEOUT, and AG_SHUTDOWN_TIMEOUT values appropriate to the ingress and scan payload size.

Production mode refuses to start unless PostgreSQL uses sslmode=verify-full and OPA uses HTTPS. The application itself does not terminate public TLS; the ingress must do so. Do not set AG_ENV=production for the local Compose stack, whose bundled PostgreSQL is intentionally configured for local development only.

## First deployment

1. Provision PostgreSQL with TLS, private networking, automated encrypted backups, point-in-time recovery, and a tested restore procedure.
2. Provision OPA on a private network. Package and review the exact Rego policy bundle that will be deployed; do not mount a writable policy directory into the running service.
3. Build the control-plane image from a reviewed commit. Scan it, record its digest, and deploy that immutable digest.
4. Inject production secrets at runtime. Do not put secrets in build arguments or Docker image environment defaults.
5. Run controlplane migrate as a one-off deployment job using the same reviewed image and database credentials. Do not run migrations concurrently from multiple replicas.
6. Start one API replica and verify GET /healthz and GET /readyz through the private network. Readiness checks both PostgreSQL and OPA.
7. Run controlplane bootstrap --organization "Customer Name" once in a controlled administrative session. Capture the owner key directly into the secret manager. It is displayed once; do not store it in shell history or CI logs.
8. Enroll TOTP for the bootstrap owner key, verify it, create least-privilege keys with expiry, and revoke the bootstrap key after an independently verified recovery owner exists.
9. Configure ingress, monitoring, alerting, backups, and incident response before allowing customer data.

## Operations and recovery

- Alert on readiness failures, elevated 4xx/5xx rates, authentication failures, ingestion latency, database saturation, OPA errors, and audit-chain verification failures.
- Keep request IDs for correlation. Redact Authorization, cookies, API keys, TOTP codes, and customer evidence from ingress, application, tracing, and error logs.
- Verify the audit chain on a schedule and export audit checkpoints to independently controlled immutable storage. The current in-database hash chain is tamper-evident, not immutable against a database superuser.
- Back up PostgreSQL with encryption and access separation. Test point-in-time restore and a full application recovery at least quarterly. Protect the API-key pepper separately; losing it invalidates every API key.
- Rotate database credentials and API-key peppers through a documented maintenance window. Pepper rotation currently requires a coordinated key re-issuance plan; do not rotate it casually.
- Apply OS, base-image, Go dependency, PostgreSQL, and OPA security updates on a defined cadence. Rebuild from source and redeploy immutable image digests.
- Restrict outbound network egress. The service should not have broad access to customer cloud control planes until provider connectors are implemented and separately reviewed.
- Do not send raw MCP config files, environment variables, command arguments, tokens, or private keys to the API. Submit normalized, redacted inventory only.

## Release gates before general availability

The following are **not delivered by the current control-plane foundation** and must not be represented as available:
- OIDC SSO, user sessions, user-level RBAC, SCIM, and IdP-enforced MFA.
- Production-validated GitHub, Okta, Microsoft Entra, and Google Workspace connectors with least-privilege scopes and provider-specific revocation semantics.
- A customer-facing browser dashboard, tenant onboarding/billing, support tooling, and account recovery.
- Runtime MCP gateway enforcement, OAuth 2.1 audience-bound credentials, and durable human approval orchestration.
- External immutable audit checkpointing, managed KMS/HSM envelope encryption, distributed rate limiting, and formal retention/deletion controls.
- Independent penetration testing, threat-model review by an external party, incident-response exercise, privacy/legal review, and a customer-facing SLA/SLO.

Before GA, complete a third-party penetration test and remediate findings; establish a vulnerability disclosure process and security contact; publish a DPA/privacy notice and subprocessor list; document data residency, retention, deletion, backup expiry, and breach notification; obtain legal review of Apache-2.0 obligations and product claims; and run a production load/chaos/recovery test with measurable SLOs.
